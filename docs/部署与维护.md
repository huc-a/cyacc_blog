# 部署与维护

cyacc.cn 已有 Ubuntu 24.04 和宿主 Nginx/证书时，使用 [ECS 专用步骤](cyacc.cn-ECS部署.md) 与 `compose.ecs.yaml`。它停用容器 Nginx，宿主分别代理本机 8088/8089；备份使用 `backup.ecs.sh`。下文默认 Compose 方案仍供没有现成宿主路由的环境参考，不要混用两个方案的启动/备份命令。

## 运行结构

前后端统一使用同域 `/api`。开发/预览由 Nuxt 代理，生产 Nginx 将 `/api` 转发给 Java，其余请求交给 Nuxt。公开页面不做页面缓存，发布、下线与回收立即生效。搜索和阅读页由 SSR 输出，后台通过服务器会话鉴权。

本地构建：`mvn -f server/pom.xml -DskipTests package`、`scripts/web.ps1 build`。配置 DB_URL/DB_USER/DB_PASSWORD/MEDIA_DIR 后运行 `java -jar server/target/caiya-server-0.1.0.jar`，前端运行 `scripts/web.ps1 preview`。开发启动流程见 README。

## Docker Compose

目标主机需要 Docker Engine 与 Compose v2+，建议至少 2 核 2 GB 内存及持久化磁盘。先检出要部署的 Git 标签：

```bash
cp deploy/.env.example deploy/.env
# 编辑 .env，填写四个互不相同的随机密码和真实域名。
# 可用 openssl rand -hex 24 分别生成密码。
chmod 600 deploy/.env
docker compose -f deploy/compose.yaml --env-file deploy/.env config --quiet
docker compose -f deploy/compose.yaml --env-file deploy/.env build
docker compose -f deploy/compose.yaml --env-file deploy/.env up -d --wait
```

从仓库根目录操作时明确指定 `--env-file deploy/.env`；进入 `deploy/` 后 `docker compose` 自动读取该文件。

启动顺序：PostgreSQL → 独立迁移进程 → Java → Nuxt → Nginx，均有依赖/健康检查。只有 Nginx 端口映射宿主机，默认 `127.0.0.1:8088`。数据库、Java、Nuxt 不直接暴露公网。

迁移使用 `blog_migrator`；Java 使用 `blog_runtime`，允许表数据与序列操作，不能建表、改表、创建角色。日常服务不接收迁移密码，且关闭自动迁移。初始化脚本只在空数据卷执行；修改 `.env` 不会自动改变已有数据库角色密码。

Java/Nuxt 以普通用户运行，根文件系统只读，媒体单独持久化。基础镜像固定到查询过的 manifest 摘要，更新时应重新扫描并测试。固定摘要不代表永久安全。

## HTTPS 与域名

宿主机 HTTPS 代理配置真实证书，将域名转发到 `http://127.0.0.1:8088`，保留 Host，HTTP 跳转 HTTPS。生产保留 `COOKIE_SECURE=true`；`SITE_URL` 设置为真实 HTTPS 根地址，用于 SEO canonical。

本轮没有用户的域名与证书，未做公网 TLS 验收。上线时验证证书链、跳转、Cookie 的 Secure/HttpOnly/SameSite 和 canonical。临时 HTTP 隔离验收可设置 `COOKIE_SECURE=false`，之后必须恢复。

## Umami

- `UMAMI_URL`：受信任的服务根地址。
- `UMAMI_API_URL`：可选的完整 API 端点，优先于 `UMAMI_URL`；Cloud 使用 `https://api.umami.is/v1`。免费采集不需要 API 密钥，见 [Umami Cloud 接入](Umami-Cloud接入.md)。
- `UMAMI_WEBSITE_ID`：统计站点 ID。
- `UMAMI_TOKEN`：仅服务端使用的读取 token，不能放入前端公开变量。
- `UMAMI_SCRIPT_URL`：浏览器可访问的 HTTPS 脚本地址，例如 `https://stats.example.com/script.js`。

浏览器仅记录公开路径，排除后台与查询参数。后台区分未配置、连接失败和真实零访问。当前适配器已通过本地 HTTP 测试，尚未连接真实实例；上线后核对浏览量、去重访客、来源和北京时间区间。

## 更新维护

升级前完整备份；阅读迁移，保留旧镜像。检出新标签并更新 `RELEASE_TAG`，重新 build/up。迁移失败时新应用不会启动，先看日志，不能手工修改 Flyway 校验和。

```bash
cd deploy
docker compose ps
docker compose logs --tail=100 migrate server web nginx
curl --fail http://127.0.0.1:8088/api/public/site
```

正式环境不要运行 `docker compose down -v`，它会删除持久化卷；该命令仅用于可丢弃的 CI 环境。

## 升级到含 V9–V11 迁移的版本

- 既有数据库需要先由超级用户执行一次 `CREATE EXTENSION IF NOT EXISTS pg_trgm`（新装环境由 `deploy/init-db.sh` 自动完成）；V10 的三字组搜索索引会在扩展不可见时静默跳过，不会让迁移失败。
- 新增可选环境变量 `TRUST_FORWARDED_HEADERS`（默认 `false`）：仅当自带 Nginx（会用真实地址覆盖 `X-Forwarded-For`）是唯一入口时才设为 `true`，此时登录限流按真实访客 IP 计数；直接暴露应用端口时保持 `false`，否则转发头可被伪造绕过限流。
- 新增可选环境变量 `AUDIT_RETENTION_DAYS`（默认 180）：操作日志保留天数，每天 03:30 自动清理更早的记录。

CI 包含真实 PostgreSQL、浏览器、恢复、权限、依赖/凭据和容器启动检查。本机已验证应用构建、Compose 解析、Nginx 转发与恢复；没有 Docker 引擎，因此容器构建/启动和首次云端 CI 仍需在目标环境验收。

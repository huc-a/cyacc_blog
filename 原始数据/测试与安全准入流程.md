对“菜牙爱吃菜”，建议把这一部分设计成 **测试与安全准入流程**：每个功能完成后都有测试，上线前有明确检查项，上线后还能验证备份和监控，而不是最后只跑一次漏洞扫描。

按照你第一版“单管理员、无访客注册”的范围，重点应放在内容发布、后台权限、Markdown、图片上传和外部链接处理。下面先确定方案，不直接写测试代码。

## 一、分成四个层次来做

|层次|检查目标|建议方式|
|---|---|---|
|业务逻辑测试|发布规则、版本隔离、有效期判断是否正确|JUnit 单元测试|
|数据库与接口测试|事务、约束、权限、接口返回是否正确|Spring Boot Test、MockMvc、Testcontainers|
|浏览器流程测试|用户能否完成登录、编辑、预览、发布等完整操作|Playwright|
|安全与上线检查|未授权访问、注入、文件、依赖、部署和恢复风险|自动扫描＋人工检查|

不要让所有测试都依赖浏览器。发布规则、时间计算、数据约束等，应该在更容易定位问题的后端测试中先验证。

## 二、优先测试内容发布，而不只是增删改查

你已经采用了版本化内容设计，最重要的是证明“草稿不会影响线上”。

建议第一批就覆盖以下场景：

|测试场景|预期结果|
|---|---|
|新建内容，仅保存草稿|公开列表、详情、搜索都查不到|
|首次发布|前台读取对应冻结版本|
|编辑已发布内容，但没有更新发布|前台继续展示旧版本|
|修改标题、摘要、封面、标签|未发布前，首页和搜索结果也不能提前改变|
|修改作品地址、羊毛条件|未发布前，线上仍保留原值|
|教程修改章节内容和顺序|未发布前，旧章节保持不变|
|发布过程中发生数据库错误|整个事务回滚，不能留下半发布状态|
|内容下线或进入回收站|所有公开入口不再返回内容|
|公开版本指针指向另一条内容|数据库或业务校验拒绝|
|两个标签页同时编辑|旧版本保存失败并提示冲突，不能覆盖新修改|

这里还要专门验证缓存：发布、下线、删除后，首页、详情和搜索不能因为缓存策略不同而出现互相矛盾的结果。

### 数据库测试使用真实 PostgreSQL

不要只用模拟对象测试数据库规则。部分唯一索引、组合外键、JSONB、事务回滚和并发冲突，都需要在 PostgreSQL 上验证。

建议用 Testcontainers 启动临时 PostgreSQL，执行正式迁移脚本，再运行测试。Spring Boot 官方支持通过 `@ServiceConnection` 对接容器化测试服务。[[docs.spring](https://docs.spring.io/spring-boot/reference/testing/testcontainers.html)]

重点验证：

- 全新数据库能完整执行迁移。
- 从上一版结构升级后，已有数据仍正确。
- 一个内容最多存在一个编辑中版本。
- 冻结版本的正文、章节、标签和媒体关联不能继续被普通编辑接口修改。
- 发布事务失败后，版本状态和指针都恢复原状。
- 并发创建版本、并发发布时，不产生重复或覆盖。

## 三、安全检查先围绕六类入口

### 1. 登录与后台接口

虽然只有你一个管理员，也不能只靠“不公开后台地址”保护网站。

建议检查：

- 未登录访问管理接口，被拒绝。
- 登录后才可以新增、编辑、上传和修改配置。
- 退出后，原会话不能继续操作。
- 登录失败有频率限制和通用错误提示。
- 后端不提供访客注册、任意创建管理员等无需求接口。
- 密码、会话令牌、Umami 凭据不出现在日志和响应中。
- 公开接口不会返回草稿、账号信息或内部配置。

第一版建议采用服务端会话方案。会话 Cookie 配置 `HttpOnly`、`Secure` 和合适的 `SameSite`，同时保留 CSRF 防护；不能因为使用 Cookie 或同域部署，就直接关闭保护。

对于会改变状态的请求，优先使用框架内置的 CSRF 防护并验证令牌；这也是 OWASP 的首选建议。[[cheatsheetseries.owasp](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)]

测试时要明确区分：

```
没有登录 → 不允许访问管理资源
已登录但 CSRF 校验失败 → 不允许修改数据
公开读取接口 → 只返回允许公开的数据
```

### 2. Markdown、链接和外观配置

这是博客里容易被低估的风险点。需要测试的内容不仅是正文，还包括标题、摘要、标签、图片说明和预览页。

建议策略：

- 默认不允许 Markdown 中直接执行原始 HTML。
- 如需支持部分 HTML，使用明确的允许列表做安全净化。
- 链接仅允许需要的协议，拒绝危险协议。
- 后台预览和前台阅读使用一致的安全处理。
- 外观配置只允许规定字段，不提供“随意写脚本”的配置入口。
- CSP 作为补充防线，不代替输出编码和 HTML 净化。

重点验收“输入被当作内容展示，而不是执行”。不同输出位置需要不同处理，不能只在入库前统一替换几个字符就认为防住了 XSS。[[cheatsheetseries.owasp](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)]

### 3. 图片上传

建议第一版对管理员上传也采取限制：

- 先允许 JPEG、PNG、WebP 等实际需要的图片格式。
- 用户上传 SVG 暂不开放；可信的内置 SVG 可以随项目静态资源发布。
- 服务端同时检查扩展名、媒体类型和实际能否解码。
- 使用系统生成的存储键，不直接使用上传文件名。
- 限制文件大小、图片尺寸和批量数量。
- 上传目录不能执行脚本。
- 删除素材前检查已发布内容和站点配置的引用。
- 图片解码与处理失败时，不能留下错误数据库记录。

OWASP 明确提醒：请求中的 `Content-Type` 可以伪造，不能把它当成唯一依据，并建议使用文件类型允许列表、生成文件名及大小限制。[[cheatsheetseries.owasp](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)]

### 4. 网站检查、图标抓取和外链预览

你的网站收藏和羊毛栏目，未来可能增加“检测链接是否有效”“自动抓网站图标”等功能。这些功能会让服务器请求用户填写的 URL，需要防范 SSRF。

第一版最简单的做法是：先不自动抓取，只保存并展示链接。

确实要抓取时，再增加：

- 限定 HTTP／HTTPS。
- 校验目标域名及解析地址。
- 拒绝访问回环、内网、链路本地等不应访问的地址。
- 重定向后的目标重新检查。
- 设置超时、响应体上限和请求频率。
- 配合网络层限制不必要的出站访问。

SSRF 防护不能只检查字符串里有没有 `localhost`；需要围绕目标域名、IP 地址及允许访问的范围制定规则。[[cheatsheetseries.owasp](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)]

### 5. 数据库访问

建议落实：

- SQL 使用参数绑定，用户输入不能直接拼接到 SQL。
- 排序字段、排序方向采用允许列表，不能原样拼接前端参数。
- 分页大小有上限，避免一次读取整库。
- 网站业务账号不使用数据库超级用户。
- 数据库迁移账号与日常应用账号按职责分开。
- 删除、发布、修改配置等敏感操作记录审计日志。
- 异常响应不暴露 SQL、堆栈和数据库连接信息。

对 MyBatis，尤其检查动态排序、搜索条件和批量操作中的字符串拼接位置，不能只看普通查询。

### 6. 统计接口与凭据

统计模块应单独测试：

- 浏览器无法获取 Umami 的服务端凭据。
- 未登录不能读取完整管理统计接口。
- 日期范围、时间格式和区间长度有校验。
- Umami 超时或不可用时，后台显示错误状态，不伪造为零访问。
- 不把原始 IP、敏感查询参数或认证信息随意作为事件属性发送。
- 计数单位与图表文案一致，不能把访客数、页面浏览数都称为会话数。

“没有数据”和“请求失败”需要在 UI 和接口中明确区分。

## 四、浏览器端至少覆盖三条主流程

使用 Playwright 跑真实页面和接口，而不是只检查生成的 HTML 字符串。

### 流程 A：内容发布

```
登录 → 新建文章 → 保存草稿 → 预览
→ 确认公开页面不可见 → 发布 → 公开页面可见
→ 改稿不发布 → 公开页面仍是旧版本
```

### 流程 B：媒体与外观

```
上传图片 → 配置背景 → 预览
→ 应用更改 → 前台更新
→ 尝试删除正在使用的图片 → 正确阻止或要求处理引用
```

### 流程 C：回收站与权限

```
内容移入回收站 → 公开页面不可见
→ 恢复 → 按既定规则恢复状态
→ 退出 → 原管理接口请求被拒绝
```

测试使用固定、可重建的数据，并优先定位按钮名称、表单标签等用户可见元素。Playwright 官方建议这样构建更稳定的测试，并使用自动等待和可重试断言，而不是依赖固定延时。[[playwright](https://playwright.dev/docs/best-practices)]

## 五、把检查接进开发流程

建议每次代码提交执行：

```
代码检查与编译
      ↓
后端单元测试
      ↓
PostgreSQL 集成测试＋迁移测试
      ↓
前端类型检查与组件测试
      ↓
关键浏览器流程测试
      ↓
依赖漏洞与敏感信息检查
```

第一版可以选择：

|工作|工具建议|
|---|---|
|后端逻辑与接口|JUnit、MockMvc|
|数据库集成|Testcontainers|
|前端组件|Vitest|
|浏览器端到端|Playwright|
|前端依赖检查|包管理器的审计工具|
|Java 依赖检查|OWASP Dependency-Check 等依赖扫描工具|
|凭据泄漏检查|Gitleaks|
|动态安全检查|后续在测试环境加入 OWASP ZAP|

不必第一天全部铺满。先把核心发布测试、接口权限测试和依赖检查建立起来。

动态扫描仅针对自己拥有或明确授权的测试环境。主动扫描可能修改数据或产生额外负载，不直接拿生产数据库做试验。

## 六、上线前还要做一次“恢复测试”

备份成功不等于能恢复。至少做一次完整演练：

1. 导出业务数据库。
2. 备份上传文件和必要配置。
3. 在隔离环境恢复。
4. 检查公开文章、教程章节、封面和背景引用。
5. 验证管理员能登录。
6. 确认恢复过程没有误连接生产服务。

数据库和图片需要有一致的恢复计划，否则可能恢复出一批“记录还在、文件却找不到”的内容。

## 七、建议的第一版上线门槛

以下项目通过后，再考虑正式开放：

- 核心发布和草稿隔离测试全部通过。
- 未登录无法调用管理接口。
- CSRF、Markdown、上传和外部请求风险完成检查。
- 数据迁移能从空库和上一版本顺利执行。
- 已知高风险问题完成修复，或有明确且经过评估的处置措施。
- 关键浏览器流程通过。
- 完成至少一次数据库与媒体恢复演练。
- 生产环境关闭调试输出，凭据不进入仓库，管理与数据库服务不随意暴露公网。

不建议把“覆盖率达到某个数字”作为唯一上线标准。对这个项目，草稿泄漏、越权修改、发布事务不完整，比普通工具函数少测几个分支更值得优先处理。

目前这些是测试与安全方案，并不表示已有原型已经通过上述检查。先前 HTML 的语法和逻辑验证，只覆盖了原型层面，不能代替正式系统的接口、数据库和安全测试。

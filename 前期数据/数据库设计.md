进一步落到“表、字段、关系、约束”层面，作为“菜牙爱吃菜”第一版数据库设计稿。

建议继续采用 **内容版本化设计**：内容主表管理身份与发布入口，版本表管理实际内容，专属详情跟随版本保存。这样才能真正做到“编辑草稿不影响线上”。

这一轮先确定结构，不直接生成建表 SQL，避免业务规则还没定清楚就把表建死。

## 二、统一字段约定

先固定这些规则，后面开发会省掉很多重复判断。

|项目|建议|
|---|---|
|实体主键|`bigint`，数据库生成|
|关联表主键|能用联合主键时，不额外增加无意义 ID|
|时间点|`timestamptz`|
|长正文|`text`|
|状态字段|`varchar`＋明确的 `CHECK` 约束|
|灵活配置|`jsonb`|
|乐观锁|`lock_version bigint`，从 0 开始|
|回收站|内容主表使用 `deleted_at`|
|文件引用|使用媒体 ID 或存储键，不散落完整域名|

不要给所有表机械地加 `deleted_at`。内容需要回收站，版本和关联记录则应有各自明确的生命周期。

唯一性、外键、非空和状态值应尽量交给数据库约束；PostgreSQL 支持这些约束，但 `CHECK` 不能代替任意跨表业务校验。[[postgresql](https://www.postgresql.org/docs/current/sql-createtable.html)]

## 三、内容主表：`content`

这张表不保存正在编辑的标题和正文，只保存内容身份及发布入口。

|字段|类型|空值|说明|
|---|---|---|---|
|`id`|bigint|否|主键|
|`content_type`|varchar(20)|否|`article/work/tutorial/website/deal`|
|`slug`|varchar(160)|否|全站唯一访问标识|
|`publish_status`|varchar(20)|否|`draft/published/offline`|
|`working_revision_id`|bigint|是|当前工作版本|
|`published_revision_id`|bigint|是|当前公开版本|
|`first_published_at`|timestamptz|是|首次发布后保留|
|`last_published_at`|timestamptz|是|最近一次发布或更新|
|`created_at`|timestamptz|否|创建时间|
|`updated_at`|timestamptz|否|内容身份或发布信息更新时间|
|`deleted_at`|timestamptz|是|非空表示位于回收站|
|`lock_version`|bigint|否|并发更新校验|

### 约束与规则

- `slug` 全站唯一，第一版限定小写英文、数字和连字符。
- 回收站中的内容仍占用原 `slug`，恢复时不会与新内容冲突。
- `publish_status = published` 时，必须存在 `published_revision_id`。
- 工作版本、公开版本必须属于当前这条 `content`，不能指向其他内容。
- 内容类型创建后不允许直接修改。
- 下线不删除公开版本指针，以便保留记录；公开查询同时检查发布状态和删除标记。

这里建议暂时不做“改地址后自动重定向”。如果以后允许修改已发布地址，再增加独立的重定向表。

## 四、版本表：`content_revision`

这里保存“某一版内容实际长什么样”。

|字段|类型|空值|说明|
|---|---|---|---|
|`id`|bigint|否|版本主键|
|`content_id`|bigint|否|所属内容|
|`content_type`|varchar(20)|否|用于强化类型约束|
|`revision_no`|integer|否|内容内部版本号|
|`revision_state`|varchar(20)|否|`editing/frozen`|
|`title`|varchar(200)|否|草稿可为空字符串，冻结前必须有效|
|`summary`|text|否|默认空字符串|
|`category_id`|bigint|是|主分类|
|`cover_asset_id`|bigint|是|封面媒体|
|`change_note`|varchar(500)|是|本次版本说明|
|`created_at`|timestamptz|否|创建时间|
|`updated_at`|timestamptz|否|工作版本修改时间|
|`frozen_at`|timestamptz|是|冻结时间|
|`lock_version`|bigint|否|防止多个标签页互相覆盖|

### 为什么需要两个版本状态？

- `editing`：可以持续修改和保存，不必每次自动保存都新建版本。
- `frozen`：发布后冻结，原内容不再直接修改。

约束建议：

- `(content_id, revision_no)` 唯一。
- 每条内容最多一个 `editing` 版本。
- 冻结版本必须有有效标题和 `frozen_at`。
- 版本类型必须与主表类型一致。
- 主分类如果限定了类型，必须与版本类型一致。

“每条内容最多一个编辑中版本”可以使用部分唯一索引表达；不要把它误写成普通的 `(content_id, revision_state)` 唯一，否则会连多个历史冻结版本也禁止掉。

### 发布与改稿流程

```
首次创建
content
  └── revision 1：editing
          ↓ 发布
      revision 1：frozen
      published_revision_id → revision 1
      working_revision_id → 空

编辑已发布内容
复制 revision 1 为 revision 2：editing
      ↓ 保存
线上仍读取 revision 1
      ↓ 确认更新
revision 2 冻结
published_revision_id → revision 2
```

发布时，版本冻结、发布指针切换和时间更新应处于同一事务中。

## 五、五类内容详情表

以下详情都以 `revision_id` 作为主键兼外键，表达“一份版本对应一份类型详情”。

### 1. `article_detail`

|字段|类型|说明|
|---|---|---|
|`revision_id`|bigint|主键，关联内容版本|
|`content_type`|varchar(20)|固定为 `article`|
|`body_markdown`|text|Markdown 正文|

第一版只存 Markdown 源文即可。HTML 渲染缓存、字数、阅读时间都可以后续增加，不要一开始就维护多份互相可能不同步的正文。

### 2. `work_detail`

|字段|类型|说明|
|---|---|---|
|`revision_id`|bigint|主键|
|`content_type`|varchar(20)|固定为 `work`|
|`body_markdown`|text|项目介绍|
|`demo_url`|text|演示地址，可空|
|`source_url`|text|源码地址，可空|
|`project_status`|varchar(20)|`planning/developing/released/archived`|
|`tech_stack`|text[]|技术栈名称列表|

项目截图复用媒体引用表，不再单独存一串图片 URL。

### 3. `tutorial_detail`

|字段|类型|说明|
|---|---|---|
|`revision_id`|bigint|主键|
|`content_type`|varchar(20)|固定为 `tutorial`|
|`intro_markdown`|text|系列介绍|
|`difficulty`|varchar(20)|`beginner/intermediate/advanced`|
|`prerequisites_markdown`|text|前置要求，可为空字符串|

### 4. `website_detail`

|字段|类型|说明|
|---|---|---|
|`revision_id`|bigint|主键|
|`content_type`|varchar(20)|固定为 `website`|
|`website_url`|text|网站地址|
|`description_markdown`|text|用途和使用说明|
|`icon_asset_id`|bigint|图标媒体，可空|

网站是否能访问属于运行状态，不写回冻结版本。否则一次链接检查就会破坏“已发布版本不可变”的规则。

### 5. `deal_detail`

|字段|类型|说明|
|---|---|---|
|`revision_id`|bigint|主键|
|`content_type`|varchar(20)|固定为 `deal`|
|`body_markdown`|text|活动说明|
|`source_url`|text|信息来源|
|`claim_url`|text|领取入口，可空|
|`benefit_text`|text|优惠或资源内容|
|`requirements_markdown`|text|适用条件与限制|
|`starts_at`|timestamptz|开始时间，可空|
|`ends_at`|timestamptz|截止时间，可空|

约束：如果开始和结束时间均存在，必须满足结束时间晚于开始时间。

人工核验结果不放在这里，放进核验记录表。活动规则属于发布内容，核验属于后续运营动作，两者应分开。

### 详情类型如何防止串表？

建议采用明确的类型约束：

```
content：(id, content_type) 唯一
   ↑ 组合外键
content_revision：(content_id, content_type)

content_revision：(id, content_type) 唯一
   ↑ 组合外键
各详情表：(revision_id, content_type)
```

每张详情表再固定自己的 `content_type`。这样，文章版本不能插入作品详情。

“冻结前必须存在且完整的对应详情”，仍需要发布事务中的完整性校验；如果希望数据库层也严格执行，再设计专门的约束触发器，不要声称普通外键已经覆盖全部规则。

## 六、教程章节：`tutorial_chapter`

第一版采用“整个教程版本一起发布”，不再额外引入每章独立发布状态。

|字段|类型|说明|
|---|---|---|
|`id`|bigint|章节记录主键|
|`tutorial_revision_id`|bigint|所属教程版本|
|`chapter_key`|uuid|章节稳定标识，复制版本时保留|
|`slug`|varchar(120)|当前教程内的章节地址|
|`title`|varchar(200)|章节标题|
|`body_markdown`|text|章节正文|
|`sort_order`|integer|排序，必须非负|
|`created_at`|timestamptz|创建时间|
|`updated_at`|timestamptz|修改时间|

建议约束：

- 同一教程版本内，`chapter_key` 唯一。
- 同一教程版本内，`slug` 唯一。
- 排序使用 `sort_order, id` 保证结果稳定。
- 所属教程版本冻结后，章节也不可直接修改。

`id` 表示这一版章节记录；`chapter_key` 表示跨版本的同一章。这样以后做版本比较时，不必靠标题猜测章节是否相同。

## 七、分类与标签

### `category`

|字段|类型|说明|
|---|---|---|
|`id`|bigint|主键|
|`content_type`|varchar(20)|所属内容类型|
|`name`|varchar(60)|分类名称|
|`slug`|varchar(80)|分类地址标识|
|`sort_order`|integer|展示顺序|
|`created_at`、`updated_at`|timestamptz|时间|

建议：

- `(content_type, slug)` 唯一。
- `(content_type, name)` 唯一。
- 第一版不做无限层级分类。
- 被版本使用的分类不直接删除；先迁移引用或保留。

### `tag`

字段：`id`、`name`、`slug`、`created_at`。

标签全站共用，名称与地址标识分别唯一。涉及大小写或空白的统一规则，需要在保存前标准化。

### `revision_tag`

|字段|类型|说明|
|---|---|---|
|`revision_id`|bigint|内容版本|
|`tag_id`|bigint|标签|

联合主键为 `(revision_id, tag_id)`，防止重复关联。

分类、标签的“关联关系”跟随版本冻结；分类和标签本身的名字属于公共词汇，重命名会反映到使用它们的内容上。第一版建议接受这一规则，不追求连标签名称也逐版本快照。

## 八、媒体表与引用

### `media_asset`

|字段|类型|说明|
|---|---|---|
|`id`|bigint|主键|
|`storage_provider`|varchar(30)|本地或某对象存储|
|`storage_key`|text|存储键，与 provider 组合唯一|
|`original_name`|varchar(255)|原始文件名|
|`mime_type`|varchar(120)|媒体类型|
|`size_bytes`|bigint|文件大小，非负|
|`width`、`height`|integer|图片尺寸，可空|
|`sha256`|varchar(64)|校验值，可空|
|`created_at`|timestamptz|上传时间|

不把 SHA-256 强制设为唯一：是否允许同一文件重复上传，应是明确的产品规则，而不是无意中被数据库限制。

### `revision_media`

|字段|类型|说明|
|---|---|---|
|`id`|bigint|主键|
|`revision_id`|bigint|内容版本|
|`media_asset_id`|bigint|媒体|
|`usage_type`|varchar(20)|`body/gallery/chapter`|
|`chapter_id`|bigint|章节引用时填写|
|`alt_text`|text|当前引用处的替代文本|
|`caption`|text|当前引用处的说明|
|`sort_order`|integer|图库或展示排序|

需要额外检查：`chapter_id` 所属教程版本必须与 `revision_id` 一致。

封面由 `content_revision.cover_asset_id` 直接引用；作品截图放 `gallery`，章节插图放 `chapter`。

冻结版本引用过的媒体不能直接删除。清理媒体时，还要检查封面、网站图标、正文引用和站点背景，不只查一张关联表。

## 九、站点配置：`site_setting`

|字段|类型|说明|
|---|---|---|
|`setting_key`|varchar(100)|主键|
|`value_jsonb`|jsonb|配置值|
|`schema_version`|integer|配置结构版本|
|`lock_version`|bigint|并发更新检查|
|`updated_at`|timestamptz|更新时间|

建议初始配置键：

```
site.basic
site.navigation
site.footer
home.hero
home.modules
theme.background
theme.glass
theme.reading
```

第一版的配置采用“后台预览，确认后直接保存”。暂时不加入配置历史表，避免与内容版本系统一起膨胀。

不要因为使用 JSONB 就给每个配置值建立索引。实际按 `setting_key` 读取即可；索引会增加写入和维护成本，应围绕查询需要建立。[[postgresql](https://www.postgresql.org/docs/current/indexes.html)]

## 十、管理员与日志

### `admin_user`

主要字段：

```
id
username
password_hash
display_name
enabled
last_login_at
created_at
updated_at
lock_version
```

- `username` 唯一。
- 只存密码哈希，不存明文密码。
- 第一版初始化一个管理员，不增加用户、角色、权限关联表。
- 登录会话若采用 Spring Session JDBC，由对应组件管理会话表，不手写另一套会话结构。

### `operation_log`

主要字段：

```
id
operator_id
action
target_type
target_id
result
request_id
detail_jsonb
created_at
```

设计为追加记录，通常不需要 `updated_at`。

`detail_jsonb` 只记录必要摘要，不保存密码、认证令牌或不受限制的完整请求正文。内容版本已经承担正文历史，操作日志不再复制一份全文。

## 十一、第二阶段的检查与核验表

### `website_check_log`

```
id
content_id
revision_id
checked_at
result               reachable/unreachable/unknown
http_status
latency_ms
error_summary
```

### `deal_verification_log`

```
id
content_id
revision_id
verified_at
result               valid/invalid/unknown
verification_method  manual/automated
evidence_url
note
operator_id
```

两张表都记录“检查的是哪一版内容”。如果活动已改成新版本，不能把旧版本的有效结论直接套在新版上。

前台羊毛状态可按以下顺序解释：

```
未到开始时间 → 尚未开始
超过截止时间 → 已过期
当前版本最新核验为 invalid → 已失效
当前版本最新核验为 valid → 已核验有效
否则 → 待核验
```

这属于业务展示规则，不需要把所有计算结果再存成一个容易过期的状态字段。

## 十二、必须重点落地的约束

|规则|实现方式|
|---|---|
|内容地址不重复|唯一约束|
|版本号不重复|`(content_id, revision_no)` 唯一|
|一个内容最多一个编辑中版本|部分唯一索引|
|版本属于正确内容类型|组合外键|
|详情属于正确版本类型|组合外键＋固定类型检查|
|发布指针不能指向其他内容|包含 `content_id` 的组合外键|
|已发布内容必须有公开版本|主表 `CHECK`|
|冻结版本不可继续修改|服务层规则；可进一步加数据库触发器|
|冻结前内容必须完整|发布事务完整性校验|
|当前版本并发保存不覆盖|`lock_version` 条件更新|
|使用中的媒体不可误删|外键限制＋引用检查|

主表和版本表存在互相引用，建表时应先创建基础表，再补充发布指针外键。必要时可使用可延迟外键，在事务结束时校验；但 `CHECK` 和 `NOT NULL` 不能因此延迟到提交时检查。[[postgresql](https://www.postgresql.org/docs/current/sql-createtable.html)][[postgresql](https://www.postgresql.org/docs/current/sql-set-constraints.html)]

最后建议把实施顺序定为：先完成 `content`、`content_revision`、`article_detail` 和发布事务，再用同一机制扩展其他四类内容。这样可以先验证最重要的“草稿隔离与发布切换”，而不是一次建完 18 张表后才发现版本模型有问题。
